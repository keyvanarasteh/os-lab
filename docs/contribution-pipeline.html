os-lab · contribution pipeline

From a claimed task to a live route

Every change in os-lab takes the same eight-step path, crosses the same five pull-request workflows, and leaves through one of four deploy surfaces. These four figures show the sequence, the selection logic inside the PR gate, the job graph of the heavy workflow, and the post-merge fan-out; the tables after them give the variations each phase actually supports.

Derived from the repository at 4390b4b · every command, path filter, shard rule and route listed here was read from the file that owns it, not inferred from convention.

01 · the spine

Eight phases, one branch at a time

A branch is only ever in one phase. The rule that keeps parallel agents from colliding is not in the diagram — it is the ownership of master: exactly one branch lands at a time, in the order the maintainer chooses.

Phase 4 is where the cost sits. run-tests.sh --changed maps changed paths to 12 stages; scripts/e2e.sh maps them to specs, routes and locales. Both read the same changed-files.sh base, so a branch never runs what it did not touch.

02 · the pull-request gate

How a pull request picks its own checks

Nothing runs the whole suite for a one-file change. Two selectors read the same change set and route it to different machinery: the Python and shell stages to the left, the browser suite to the right. Every workflow a change triggers still has to report before the branch is landed.

The verdict is not one job. unit, dashboard-e2e, content and firewall-lab each report independently; a change touching console/** or a requirements file selects every unit stage, which is the case the fan-in exists for.

03 · inside the heavy workflow

dashboard-e2e, job by job

This is the only workflow that starts browsers, so it guards its own cost. plan refuses a pull request that commits dashboard/dist and decides whether the browser job runs at all; check runs in parallel and never waits for it.

Shard count is derived, not configured. A PR gets 1 shard for a small spec set, 2 once four or more specs are affected, and master runs the whole suite across 4. The report job uploads an HTML report only when browser did not succeed.

04 · after the merge

Four deploy surfaces, only three of them in CI

A merge to master is not a deploy. Two workflows publish on a master push; the update feed is the near miss — it starts on a release event and a 20-minute cron, never on the push itself. The public site is the only surface outside CI, built and force-pushed from a maintainer's machine.

The public site is a filter, not a mirror. deploy-page.sh copies the build and deletes everything the allowlist does not name, so the Pages copy keeps firewall, source, cleanup, how-to-use, contribute, legal and feedback — and drops every console-backed route.

06 · the workflows

Every workflow a pull request can start

Path filters are the reason a docs-only change does not start browsers. Two entries here never run on a pull request at all; they run after merge or on a schedule.

caveat As of this commit master has no required checks or reviews — dashboard-dist.yml says so in the comment that lets it merge its own PR. Locale surface

Eight locales, unevenly

FIREWALL_LOCALES is en tr de fr es it fa ar. The seven non-English locales each get every route the shared [locale]/[...rest] enumerates — including /labs/ for six of the eight lab ids; winapps and web-lab stay English only.

Pages allowlist

What survives the copy

index, 404, firewall, source, cleanup, how-to-use, contribute, legal, feedback. Anything else is deleted from the published tree.

Stop rules

Three that bite

  • Never commit dashboard/dist — CI refuses the PR.
  • At most two or three heavy agents on a laptop.
  • One agent lands on master at a time.
